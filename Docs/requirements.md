# Bridge — 要件定義

## 1. プロジェクト概要

### 1.1 題材
SES業界の「営業とエンジニアの情報非対称性」を解消するための業務管理システム。
案件・技術者マッチングを軸に、営業側の商流管理と、エンジニア側のキャリア・契約可視化を両立させる。

### 1.2 背景・動機
一般的なSFAは「営業のためのツール」として設計されており、エンジニア(=商材)は管理される客体にとどまる。
SES業界では以下のような情報非対称性が現場の痛みとなっている:

- 営業がエンジニアの現場状況や希望を把握できていない
- エンジニアは自分の契約更新タイミングを直前まで知らされない
- エンジニアの希望と違う種別の案件にアサインされる
- エンジニアは自分の市場価値や単価推移を把握できない

本システムは、**営業ビューとエンジニアビューの両方**を提供することで、この情報非対称性を構造的に解消することを目指す。

### 1.3 プロジェクト期間
1ヶ月(GW期間を含む)

## 2. ペルソナ

### 2.1 ペルソナA:営業担当 佐藤(34歳・SES営業歴5年)
- **役割**:案件獲得、技術者アサイン、契約管理、KPI達成
- **日常業務**:新着案件のチェック、技術者の稼働状況確認、マッチング、スキルシート提案、面談調整、契約更新交渉
- **使っているツール**:Excel/スプレッドシートで案件一覧、技術者一覧、提案履歴を別々に管理
- **痛み**:「誰が空くのか、誰のスキルが合うのか、直近の提案履歴、全部を横断的に見られない」
- **KPI**:月間提案数、決定率、稼働率、平均単価

### 2.2 ペルソナB:エンジニア 田中(28歳・Web系志望だが現案件はパッケージ導入)
- **役割**:現案件で稼働、次の案件を探したい
- **日常業務**:現場業務、スキルシート更新(年1回程度)、契約更新時の営業との面談
- **使っているツール**:ほぼなし。契約情報は紙かPDF、スキルシートはWord
- **痛み**:
  - 契約更新時期を直前まで知らされない
  - 自分の希望キャリア(やりたい技術、避けたい業務)が営業に伝わっていない
  - 次の案件候補がどれくらいあるのか、自分の市場価値がいくらなのか全く見えない
- **望むこと**:自分の情報を自分で管理し、次の案件選択に能動的に関わりたい

| API スタイル | 緩めのREST、JSON は camelCase | Day3 |
| OpenAPI 仕様 | Swashbuckle でコードから自動生成 | Day3 |
| デプロイ先(フロント) | Vercel(無料) | Day5 |
| デプロイ先(API) | Fly.io(shared-cpu-1x、月数百円) | Day5 |
| デプロイ先(DB) | Supabase Free tier | Day5 |
| CI/CD | GitHub Actions | Day1 |

### 4.2 認可方針
- **RBAC**(ロールベースアクセス制御)
- 3ロール:Sales / Engineer / Admin
- **APIレベルで確実に弾く**(フロントの出し分けだけに依存しない)
- ASP.NET Core の `Microsoft.AspNetCore.Authentication.JwtBearer` を採用
- JWT に `sub`(UserId)、`role`、`engineerId` or `salesId` を埋め込む
- Policy-based Authorization でエンドポイント単位の認可
- リソース単位の認可(例:Engineer は自分の情報のみ編集可)は Authorization Handler で実装

### 4.3 ロール別権限

| ロール | 権限概要 |
|---|---|
| Sales | 全案件・全技術者・全契約の閲覧と編集 |
| Engineer | 全案件の閲覧(編集不可)、自分の技術者情報・契約情報のみ閲覧と編集 |
| Admin | 全権限 + ユーザー管理 |

### 4.4 認証方式選定理由
SPA(Vercel)とAPI(Fly.io)を**別ドメインにデプロイするクロスオリジン構成**のため、セッションCookieよりも JWT の方が素直に扱える。MVP ではリフレッシュトークンを省略し、アクセストークンを 24時間有効にすることで実装コストを抑えた。本番運用レベルではリフレッシュトークン方式(HttpOnly Cookie 保管)が望ましいが、MVP のスコープから外している。

### 4.5 CORS 設定
- ASP.NET Core の CORS ミドルウェアで明示的な許可リスト方式
- 許可オリジン:
  - 本番:`https://<bridge-vercel-url>`
  - ローカル開発:`http://localhost:5173`
- 許可メソッド:`GET, POST, PATCH, DELETE, OPTIONS`
- 許可ヘッダ:`Authorization`, `Content-Type`
- クレデンシャル(Cookie): 不要(JWT は Authorization ヘッダ送信のため)
